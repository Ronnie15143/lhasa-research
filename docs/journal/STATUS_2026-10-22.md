## 一、已解决：KASLR slide（原交接文档的"唯一阻塞点"）

```
slide        = 0x2971200000        (本次 boot)
_text        = 0xffffffe9f1200000
selinux_state= 0xffffffe9f3b59630  ← 阶段 A 目标
init_task    = 0xffffffe9f38bf240
init_cred    = 0xffffffe9f38d2a50
```

**11 个内核函数各自独立算 slide，结果完全一致，spread = 0；另一次抓取 427/427 条记录全票通过。**
方法见 `KASLR_SOLVED.md`：从本机 4.0.21.0 完整 OTA 里用 HTTP Range 只抠 `boot` 分区（实下 13 MB），
得到真实 `Image`，再用 `vmlinux-to-elf` 恢复出 139,213 个符号。

### 顺带纠正交接文档里的两处错误

1. **原符号配对是错的**（按频次猜的）。实测：
   - `0xffffffe9f09aa2a8` = **i2c_dw_xfer+0x1c8**（模块 `xring_i2c`），**不是** worker_thread；
   - `0xffffffe9f13d6710` = worker_thread+0x248；
   - `0xffffffe9f13d8d50` = rcu_gp_fqs_loop+0x154。
   raw 里混着模块地址，按频次配对必然错位 —— 这就是"33 个候选收敛不了"的真正原因。
   正确做法：raw 记录是 **4 字节 ring 头 + 32 字节 payload**，`payload+4 = common_pid`、
   `payload+8 = event.pid`、`payload+16 = caller`；冻结窗口后同时抓文本 trace 与
   `per_cpu/*/trace_pipe_raw`，按 (cpu, common_pid, event.pid) 精确配对。工具 `pair_records.py`。
2. **不需要 AOSP GKI prebuilt**：`kernel/prebuilts/6.18/arm64` 只有 6.18.16 且 stock 配置，
   布局与我们差 ±9 MB、连函数相对顺序都不同（`spi_transfer_wait` 在 stock 是模块、在本机是核心 text）。

## 二、已确认：竞态在本机确实打中

```
空闲基线     420  630
probe3 跑完   530  714   ← total 比基线 +84
等 5s / 10s  530  714   ← 完全不回落 = 悬空 rb_node 持久存在
```

命令：`cve64560_probe3 40 400 8 4`（40 轮 × 8 并发 × 400 timers × 4 deleter 线程）
本轮复现成功，与上一会话的 +84 一致。

**竞态时序要点**（这是关键）：
- v33 让 exec 等到"已删 40/400"再放行 → 400 次 delete 只要几十微秒，
  execve 走到 `de_thread()` 时风暴早结束 → **300 轮 / 4800 execs 零命中，active 不动**。
- probe3 在**删除线程刚进循环**时就放 exec → 能中。
- 但 probe3 的删除线程在 victim 内，`execve` 一进 `flush_old_exec()` 就把它们全 zap 掉
  → 剩余 timer 活到进程退出才释放 → 空 slab 回不到 buddy（实测 attempt=1 slab 1721/2100，
  排空门永远过不去）。

## 三、当前唯一阻塞点：整页接管（reclaim）不成功

### 证据（两个结构、两种 oracle、各 200~400 轮，全部落空）

| 结构 | 轮数 | execs | 目标 | 结果 |
|---|---|---|---|---|
| `t64560_v33`（父进程建/删 timer，exec 等 40 个） | 300 | 4800 | selinux_state | leaks=0，enforce=1 |
| `l61`（probe3 竞态 + 无条件喷 8000 frag） | 400 | 3200 | **0xdeadbeefdead0000** | 无 panic、无重启 |
| `l60`（父进程建/删 timer + exec 与风暴同时放行） | 200 | 3200 | **0xdeadbeefdead0000** | 无 panic、无重启 |

**毒化地址这一手是决定性的**：只要悬空节点所在页被我们的 8KB frag 接管，
`cleanup_timers → timerqueue_del → rb_erase` 就必然解引用 `0xdeadbeefdead0000` 而 panic。
400 轮一次都没有 → **页根本没被接管**，问题不在"竞态没中"，而在 reclaim。

### 根因（实测数据）

`posix_timers_cache` 在风暴+排空之后：

```
基线            510  714
风暴排空后      781 2772     ← total 不降反升
```

`objperslab=21`、`pagesperslab=2`（order-1，8 KB）都跟参考实现一致，
但**空 slab 大量滞留在 SLUB 的 partial 链上，没有真的 discard 回 buddy**
（`min_partial` + per-cpu partial 都会留一批）。页到不了 buddy，
我们的 `send()` 就拿不到那块页 → 内容可控的节点永远铺不上去。

`reclaim_test` 也印证：单进程建 8000 / 删 8000 后 total 只从 8421 降到 861，之后就不再降。

### 下一步（按优先级，参考实现文档 148 §6 也指出过这一点）

1. **给 SLUB 施压，强制 discard 空 slab**：
   先制造内存压力（大块 mmap 反复 touch / 大量 pipe buffer 占用），
   让 `shrink_slab` 把 partial 链上的空 slab 还回去，**再**喷 frag。
   这是当前最可能修好 reclaim 的一招。
2. **把 frag 数量拉满并改分配路径**：14746 个 order-1 页以上；
   或改用 `msg_msg`/`pipe_buffer` 等不同 order 的分配器匹配那块 slab。
3. **先落地、后写**：先用毒化地址把"接管成功"打成 panic 拿到硬证据，
   再换回 `selinux_state`，避免在同一轮里同时赌 reclaim 和写原语。
4. 若都不行：回到 doc 154 §8 的 cred 路线（`collect_posix_cputimers` 把 `current` 写回我们的页），
   但那条路同样依赖 reclaim，所以仍要先解决第 1 点。

## 四、一旦 reclaim 打通，后续已经全部就绪

```
阶段 A: t64560_v33 / l60 写 *(selinux_state) = 0  → enforcing=0, initialized=0
        ↓  (不需要 root：SELinux 关掉后 hypsys_system(uid 0) 的任意文件写就不再受限)
阶段 B(跳过): 不用 kprobe、不用 cred、不用 LKM
最终: code 7 往 /data/block/by-name/misc 写 1 字节 'K' (0x4b) → misc[0:4]=0x4b → 永久解锁
```

> 重要发现：本机 `CONFIG_STATIC_USERMODEHELPER=y` 且 `PATH=""`
> ⇒ core_pattern / modprobe_path / uevent_helper 这一整类"内核以 root 执行我们的东西"
> 的通道全部作废（与参考实现 doc 157 一致）。
> 但**不需要它们**：SELinux 一关，`miui.mqsas.IMQSNative` 的 code 7（uid 0 任意文件写）
> 就能直接写 `misc_block_device`，`code 7` 实测是"干净写入，无头无尾"，
> 写 1 字节 `K` 即把 `misc[0:4]` 变成 `4B 00 00 00`。
